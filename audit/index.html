How this is measured

Speed (lag). Every minute we record each source's vote count for each race, statewide and by county, with the time we first saw each new count. When civicAPI shows a count, we find when the state site first showed the identical count (same Democratic and Republican votes). Lag = civicAPI's time minus the state's time. Positive means civicAPI is behind. Resolution is about one minute; county lags only use exact matches. When civicAPI's statewide count never matched one the state showed exactly, the state's first count at least that large is used instead (counted as approximate).

Accuracy. (1) Counties both sources mark fully reported must match exactly, checked only when the state's count hasn't changed since civicAPI's reading. (2) Whenever a county's total is the same in both sources, the Dem/GOP split must be too; a different split means votes credited to the wrong candidate.

civicAPI refresh. How often civicAPI's own "last updated" stamp changes for each race.

State counties are fetched when the state's own county status changes (NC import time, GA percent reporting), plus a rotating backstop, so a county's first-seen time on the state side can be up to a few minutes late if many counties report at once; that would make civicAPI look faster, not slower.

Texas isn't included: the Texas Secretary of State's results site hadn't published tonight's election feed as of 4:50 pm. DDHQ isn't included: its terms of service prohibit scraping its data.
